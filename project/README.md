# Сбор данных Polymarket в ClickHouse

Сбор UP-стаканов BTC, ETH, SOL и XRP на 15-минутных рынках, цен Chainlink
и TWAP за 30/60 секунд. Торговля и расчёт теоретической цены не выполняются.

## Запуск и выбор криптовалют

1. В `.env` отдельно включите стакан и спот каждой валюты:

   ```dotenv
   BTC_ORDERBOOK_ENABLED=true
   BTC_SPOT_ENABLED=true
   ETH_ORDERBOOK_ENABLED=false
   ETH_SPOT_ENABLED=false
   SOL_ORDERBOOK_ENABLED=false
   SOL_SPOT_ENABLED=false
   XRP_ORDERBOOK_ENABLED=false
   XRP_SPOT_ENABLED=false
   ```

   Это пример для одного BTC. В текущем `.env` первоначально сохранены все четыре
   валюты. `true` включает поток, `false` отключает. Переключатель спота также
   управляет TWAP30/TWAP60 этой валюты. Допускаются только `true` и `false`;
   опечатка останавливает запуск до подключения к площадке.
   Явные переключатели имеют приоритет над прежними `POLY_SYMBOLS` и `SPOT_SYMBOLS`.
   Если переключатель отсутствует, применяется прежний список.

2. Из папки проекта выполните:

   ```sh
   python3 project
   ```

   Эта же команда работает из родительской папки `Desktop/python`.
   Запускаются два отдельных процесса: стаканы и спот. При наличии `.venv`
   автоматически используется Python из нее. Можно запускать и по прямому пути:
   `.venv/bin/python project`. `start.command` также запускает оба процесса.

3. Для остановки нажмите Ctrl+C и дождитесь завершения записи очереди.
   После изменения `.env` перезапустите команду. Обычный запуск не ограничен
   по времени; новый проверочный прогон запускается после выбора валют.

После каждого подтвержденного сохранения пакета в ClickHouse терминал показывает
криптовалюту, таблицу, количество записанных строк и общее количество для этой
криптовалюты и таблицы за текущий запуск. Например:
`[СТАКАН BTC] pricechange_v2 | записано строк: 250 | всего за запуск: 1250`
или `[СПОТ ETH] crypto_prices_v2 | записано строк: 3 | всего за запуск: 30`.
Если в пакете несколько криптовалют, для каждой выводится отдельная строка.
При запуске также перечисляются включенные в `.env` потоки.
Сообщений `Процесс идет` по таймеру нет. Ошибка и восстановление выводятся при
изменении состояния. `COLLECTOR_LOG_ENABLED=false` отключает вывод сборщиков.
Счетчики включают дозапись старой очереди и обнуляются при перезапуске процесса;
они считают подтвержденные вставки, а не проверяют уникальность всех строк базы.
Подробности ошибок сохраняются в `.collector/*-errors.log` и журнале базы.

Когда все переключатели одного процесса выключены, он ждет остановки без
подписки и записи в базу. Старая очередь этого процесса остается на диске
до следующего запуска с включенным потоком. Второй процесс работает независимо.

При аварии одного процесса запускается повторно только он, с увеличением
паузы, максимум пять раз за один запуск. Повторный совместный запуск в той же
папке состояния блокируется. На macOS во время работы блокируется сон от
бездействия; крышку оставляйте открытой.

### Подготовка на новом компьютере

Нужны Python 3.10+ на macOS/Linux и доступная база ClickHouse.

1. Создайте окружение и установите зависимости:

   ```sh
   python3 -m venv .venv
   .venv/bin/python -m pip install -r requirements.txt
   ```

2. Если `.env` отсутствует, скопируйте шаблон:

   ```sh
   cp -n .env.example .env
   ```

3. Заполните адрес, пользователя, пароль и имя базы. База должна существовать;
   таблицы создаются автоматически. Приоритет настроек: переменные окружения,
   затем `password.env`, затем `.env`. После изменения перезапустите процессы.

Для раздельного запуска используйте `.venv/bin/python ws_ingest.py` и
`.venv/bin/python spot_ingest.py` в разных терминалах. Они учитывают те же
переключатели. `CH_HTTP_COMPRESSION=true` включает сжатие записей для базы.

## Таблицы нового сбора

С 22 сентября 2026 года стандартный запуск пишет в отдельные таблицы `*_v2`.
Прежние таблицы сохранены как архив; их схемы и старые записи не изменяются.
Старые переменные `ORDERBOOK_TABLE`, `SPOT_TABLE`, настройки сетки и
`POLY_MAX_MATCHED_MARKETS` к новому сбору не применяются.

| Таблица | Содержимое |
| --- | --- |
| `orderbook_v2` | Один начальный полный снимок для каждого UP-токена рынка за запуск, в том числе пустой. Стороны `bids`/`asks` содержат JSON-массивы `[цена, объём]`. |
| `pricechange_v2` | Только изменившиеся UP-уровни: сторона, точная цена, новый абсолютный объём `size` и разность `delta`. Сюда же записываются отличия при повторном снимке от сервера. Это изменения заявок, не сделки. |
| `raw_events_v2` | Сообщения после обработки PING/PONG. У сообщений `book` сохраняется только заголовок с `snapshot_levels_omitted=true`, без `bids`/`asks`, чтобы не дублировать полные стаканы. Остальные сообщения сохраняются целиком; сервер может включать DOWN в общий пакет. |
| `book_checks_v2` | Проверки состояния стакана, признаки пересечения и несовпадения лучших цен. Сообщения `venue_bbo` сохраняют объявленные площадкой цены в `details.reported_bid/ask`. |
| `trades_v2` | Сообщения о последних сделках UP. |
| `crypto_prices_v2` | Цены Chainlink и TWAP 30/60 секунд, символ, время источника, полная точность. |
| `market_metadata_v2` | UP-токен, границы интервала, окно TWAP и полный ответ Gamma с правилами/доступными параметрами и результатом. |
| `collector_log_v2` | Запуски, подписки, смена рынков, разрывы соединений и состояние очереди. |

Цены и объёмы хранятся десятичными строками без округления к сетке 0.001.
Для расчётов преобразуйте их в `Decimal`. Нулевой `size` удаляет уровень.
Двум сторонам по одной цене соответствуют разные уровни.

После первого снимка повторные полные списки уровней не записываются ни в
`orderbook_v2`, ни в `raw_events_v2`. Полученный от сервера снимок сравнивается
с текущим состоянием в памяти: сохраняются добавления, изменения объёма и
удаления уровней (`size=0`, отрицательная `delta`). Если отличий нет, остаётся
только запись проверки. Изменения с нулевой `delta` не сохраняются.
Каждый новый 15-минутный рынок получает свой начальный снимок, как и новый
запуск программы. Переподключение в рамках того же запуска и рынка новый
полный снимок в базу не добавляет.

## Порядок и обработка данных

Все строки содержат `run_id`, `connection_id`, `seq`, `event_index`, `row_index`
и устойчивый `event_id`. В новых запусках `seq` задаёт порядок получения
внутри потока рынка за весь запуск и продолжается после переподключения;
`event_index` - порядок внутри сообщения, `row_index` - порядок изменений.
После переподключения создаётся новый `connection_id` и ожидается свежий
снимок от сервера. До его получения изменения стакана не применяются.
Состояние до разрыва остаётся в памяти; отличия свежего снимка записываются
как корректирующие дельты. Проверка помечает их причиной `reconnect`.
Это восстанавливает состояние на момент снимка, но не пропущенные события
внутри разрыва. Начало и конец разрыва остаются в журнале.

`recv_ts_ns` - время приёма Unix UTC в наносекундах; `event_ts_ms` - время
источника в миллисекундах, либо 0 для событий без такого времени. Московский
часовой пояс применяется при отображении. Часы компьютера и площадки могут
расходиться; их разность сама по себе не доказывает сетевую задержку.

При чтении используйте `SELECT ... FROM polyk.pricechange_v2 FINAL` (аналогично
для других таблиц) или удаляйте повторы по `event_id`. После неоднозначного
ответа базы пакет может быть отправлен повторно; `ReplacingMergeTree` убирает
физические повторы при слиянии, а `FINAL` обеспечивает их исключение при чтении.

Для восстановления стакана:

1. Разделите данные по `run_id`, `market` и `asset_id`, сохраняя последовательность при смене `connection_id`.
2. Объедините снимки и изменения в порядке `seq`, `event_index`, `row_index`.
3. Начальный снимок задаёт обе стороны, даже если они пусты.
4. Каждое изменение присваивает абсолютный `size` уровню `(side, price)`;
   при нуле удаляет его. Не суммируйте `size` как дельту.
5. Учитывайте `book_checks_v2` и журнал разрывов при отборе данных для модели.

Новый режим отмечен в событии `startup` полем
`book_storage=initial_snapshot_then_deltas`. Ранее собранные данные остаются
в прежнем формате: снимки заменяли обе стороны, а `seq` начинался заново
для каждого соединения. Старые скрипты сверки из `reports/` опираются на тот
формат; их нельзя применять к новым запускам без адаптации. Для нового режима
стакан восстанавливается из начального снимка и дельт, а не из заголовков `book`
в `raw_events_v2`.

Площадка может прислать лучшие цены раньше связанных изменений уровней и
разбить одну операцию на несколько сообщений. Поэтому промежуточное
несовпадение отмечается, а после согласованного изменения статус восстанавливается.
Несогласованность дольше 2 секунд вызывает запрос свежего снимка через
текущее соединение. Прием и обработка уже полученных сообщений продолжаются;
стакан остается недостоверным до нового снимка от сервера. Отличия снимка
также сохраняются дельтами с причиной `resync` в записи проверки. Если площадка не присылает
снимок за 15 секунд, выполняется переподключение. Отсутствие начального снимка
и зависший поток цен также отслеживаются. `valid` проверяет наблюдаемые лучшие цены и
пересечение; это не доказательство полноты всей глубины. Сохранённые сообщения,
начальный снимок, дельты и журнал проверок позволяют исследовать спорные участки.

Начальные исторические пакеты RTDS типа `subscribe` сохраняются в исходном
виде, но не выдаются за новые наблюдения. Таблица цен содержит `update`.
TWAP берётся из соответствующего потока площадки; поле `twap_seconds`
метаданных определяет окно конкретного рынка.

## Переход между рынками и сохранность

Следующий рынок определяется по точному slug и проверенным меткам Up/Down.
Подписка начинается за 45 секунд до открытия; предыдущая остаётся ещё
10 секунд после закрытия. Поиск метаданных не блокирует приём сообщений.

Метаданные опрашиваются и после окончания интервала, пока Gamma не сообщит
`resolved`. Список ожидающих рынков хранится локально и загружается при следующем
запуске. Если остановить сбор до публикации результата, результат появится
после следующего запуска и успешного опроса Gamma.

Запись в базу идёт через локальную очередь SQLite в `.collector/`. Медленная
или временно недоступная база, в том числе при старте, не блокирует прием
WebSocket. Таблицы создаются и запись повторяется в фоновом потоке.
Переполнение очереди обработки вызывает ожидание, а не удаление сообщений.
Текстовые PING работают независимо от обработки данных; дополнительный
таймер протокольного PING отключен. Если 60 секунд нет ни данных, ни PONG,
соединение восстанавливается. Параметры heartbeat сверены с
[документацией Polymarket](https://docs.polymarket.com/market-data/realtime-data). При штатной остановке все принятые записи
переносятся в очередь на диске; неотправленный остаток отправляется при следующем
запуске. Не удаляйте `.collector/`, пока в очереди есть данные.

При аварийном завершении или отключении питания возможна потеря последних
сообщений, ещё не перенесённых из памяти на диск (обычно до 0.25 секунды,
при нагрузке больше). Сообщения, не доставленные площадкой во время обрыва,
не восстанавливаются. Разрывы сохраняются в журнале, старый стакан через
них не продолжается.

## Файлы и проверка

- `collector_v2.py` - подключения, смена рынков, метаданные и ценовые потоки.
- `collection_book.py` - точное состояние UP-стакана и проверки.
- `collection_store.py` - схемы таблиц и очередь на диске.
- `ws_ingest.py`, `spot_ingest.py` - привычные точки запуска; старые функции
  сохранены для совместимости с архивом.
- `project`, `__main__.py`, `run_collectors.py`, `start.command` - совместный запуск и остановка.
- `collection_config.py` - независимые переключатели валют и потоков.
- `collection_console.py` - количество строк после каждого подтвержденного сохранения.

```sh
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m unittest discover -s модель -v
```

Тесты работают без внешних API и рабочей базы. `COLLECTOR_RUN_SECONDS`
можно задать для ограниченной по времени проверки; обычный запуск не ограничен.
`.env`, локальная очередь и кэш Python исключены из Git.
